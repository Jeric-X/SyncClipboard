# 历史记录导出设计

状态：已实现，平台验证结果见文末。日期：2026-10-09。

[Issue #320](https://github.com/Jeric-X/SyncClipboard/issues/320) 希望将历史记录导出为可读、可长期保存的数据。本期只实现客户端本地历史导出：历史记录设置页导出全部记录，历史记录窗口在多选模式下导出选中记录；两个入口共用独立的导出模态窗口。有附件时自动生成 ZIP，无附件时自动生成 JSON。

## 范围和设计决策

本期包含 Avalonia 和 WinUI3 两套界面，以及 Core 中共用的导出逻辑。不实现导入、配置备份还原、数据库替换、旧数据库迁移、Excel 导出、定时导出或远端历史下载。

导出格式不提供手动选择，不提供“仅导出元数据”或“排除附件”选项。所有类型统一导出其传输文件，每条记录最多对应一个附件。导出层不解释或重组传输文件内部结构。只导出完整记录；内容缺失、损坏或无法读取时跳过整条记录，归档中不保留其元数据或残缺附件。操作结束后将未导出的记录及原因写入独立报告文档，并在结果窗口提供报告路径。

先选择保存目录，再展示数量和估算大小，用户开始后从传输文件直接流式写入目标。已有附件不复制到临时目录，也不在内存中组装整个归档。最终完整记录中有传输文件时生成 ZIP，仅剩无需文件的记录时生成 JSON，没有完整记录时只生成未导出报告。短文本内联保存，长文本保留文本传输文件，Group 保留传输 ZIP，其他类型同样使用各自的传输文件。

未来新增类型沿用相同约定，由 Profile 提供传输文件及其完整性验证。导出层只依赖统一传输能力，不维护类型白名单，不随新增类型增加文件收集、解包或目录重建分支。

导出不改变历史记录、访问时间、收藏、置顶、同步状态、保留策略或当前剪贴板，不触发上传或下载，不停止全局同步服务。缺少现成传输文件但本地内容完整时，可通过现有 Profile 流程生成可复用的传输文件；不为已有附件建立导出副本。

选择保存目录后，模态窗口展示待导出条目数量和估算大小，由用户点击“开始导出”。不检查磁盘剩余空间；实际文件操作失败仍按失败流程处理。

| 位置 | 当前行为 | 本期接入 |

## 导出入口和范围

### 历史记录设置页

增加独立的“导出历史记录”设置项，描述为“导出内容完整的本地历史记录”，按钮为“导出”。点击打开导出模态窗口，范围固定为“全部历史记录”。

全部记录指预估阶段数据库快照中 `IsDeleted == false` 的客户端本地记录，包含收藏和置顶记录。它不受历史窗口的搜索、类型筛选、分页和排序状态影响，也不读取服务器上尚未存在于本地数据库的记录。

历史功能关闭但本地仍有记录时，仍允许导出。先选择目录，预估阶段确认没有记录时显示“没有可导出的历史记录”，不生成空归档。

### 历史记录窗口

仅在多选操作栏提供“导出”按钮。命令执行时复制 `selectedHistoryRecords.Keys`，之后选择变化不改变此次请求。范围包含跨筛选、跨分页的全部已选记录，不只包含当前可见记录。

快照查询时已经删除或不存在的已选项计入跳过数量，并在结果中说明。全部已选项均不可用时不生成归档。成功、取消或失败后均不主动清空选择、不退出多选模式。

内部用 `selected == null` 表示全部记录，非空键集合表示所选记录；空键集合不能被解释为全部记录。界面不再增加时间、类型等筛选器，需要限定范围时使用历史窗口的现有筛选和多选功能。

## 共用导出模态窗口

新增独立的 `HistoryExportDialog` 和共用 `HistoryExportViewModel`。独立指具有自己的视图、状态和完整导出生命周期，不将流程嵌入设置页或多选栏。

Avalonia 使用专用 `FAContentDialog`，WinUI3 使用专用 `ContentDialog`，遵循已有编辑对话框的模式。两个入口在各自平台复用同一组件；每次打开创建新的 ViewModel，不共享前一次导出的进度和取消令牌。

窗口包含：

- 标题“导出历史记录”，以及“全部历史记录”或“选中的 N 条记录”。
- 开始前显示本次选择的总条目数量（设置页入口为全部记录数量）和估算大小，例如“预计导出 128 条记录，大小约 240 MiB”；准备失败的记录不在预处理界面提示，原因保留到最终结果和报告。
- 已选保存目录和“更换位置”入口，开始导出后固定目录。
- 界面仅显示数量、预计大小、保存位置和必要结果，不展示 JSON/ZIP 格式规则等实现细节。
- 预估及流式导出阶段的进度，当前记录数及已处理字节数；尚未知总量时显示不定进度。
- 完成后显示成功导出数量；文件缺失或其他失败数量大于 0 时才显示对应项，全部成功时仅显示“已导出 N 条记录”。结果窗口和报告摘要使用相同规则。
- 导出文件和未导出报告的完整路径分别显示“备份文件”和“未导出记录报告”标题；只提供“打开文件夹”，不直接打开文件或报告。
- 随状态变化的“开始导出”“取消”“关闭”按钮。

窗口按阶段展示：预估和导出中仅显示进度、当前状态与取消；待导出显示范围、目录、数量、大小、更换位置、可用的开始按钮和关闭；结束后隐藏范围、目录设置、开始及进度，仅保留结果、带标题的已生成文件路径、“打开文件夹”及关闭。仅存在导出文件或报告时提供打开文件夹。预估失败或取消后可更换位置重新准备；正式导出结束后不重复执行本次计划。

正常流程为：

```text
先弹出目录选择器
  → 用户选择保存目录
  → 打开导出模态窗口，查询快照并估算大小
  → 展示待导出条目数量和估算大小
  → 开始导出
  → 逐条取得并验证传输文件，跳过不可导出的记录
  → 从源文件直接流式写入所选目录中的归档
  → 根据实际完整记录完成 ZIP 或 JSON 并提交
  → 在同一目录将未导出记录及原因写入独立报告
  → 在原模态窗口显示成功导出数量、因缺失文件未导出数量和报告路径
```

跳过缺失文件的记录后直接继续，不增加“保存不完整记录”的确认步骤。若最终没有完整记录，仅在已选目录保存未导出报告并显示数量和路径，不生成空归档，也不重新询问位置。

选择的是目录，而非带固定扩展名的文件。文件名主体为 `SyncClipboard-history-yyyyMMdd-HHmmss`，最终根据实际结果采用 `.json` 或 `.zip`；同名追加编号，不覆盖已有文件。导出中途不再弹出位置或格式选择器。

取消最初的目录选择器即结束本次入口操作，不生成任何文件。实际导出过程中关闭窗口或按取消，先取消任务、释放句柄并删除本次未提交输出，再保存报告并进入结果状态。已提交的最终文件不再报告为取消。

同一进程同时只允许一个导出流程，另一个入口提示已有导出正在进行；此限制只针对导出，不阻塞其他历史操作。

### 导出前预估

位置选择完成后异步查询快照并估算，不阻塞界面。预估完成后启用“开始导出”，用户可在预估中或查看结果后取消。导出前显示的条目数量为本次选择的总量，包含准备失败及已失效的选择；设置页入口显示本次快照的全部记录数量。预计大小仍仅统计准备成功的记录，失败原因保留到最终报告。

估算指最终导出文件的预计大小，不是所需磁盘空间。它由 JSON 文本及元数据的预计 UTF-8 编码大小、可用传输文件大小和外层 ZIP 条目开销组成，不预先假定外层压缩能节省空间，也不将字符数直接当成字节数。

- 已有传输文件：调用 Profile 的统一准备和验证能力，再读取文件长度；旧记录沿用 Profile 的原文件路径回退。验证可能读取完整文件并计算哈希。
- 尚需生成的传输文件：本地内容完整时调用统一 `PrepareTransferData` 能力，在正常历史存储位置生成传输文件并计入大小。准备阶段填好记录的 `transferData`（名称、归档相对路径、实际长度和哈希），本机源路径仅保留在本次导出计划中，供正式导出直接复用，不写回数据库；不新增类型分支或下载内容。
- 无法准备或无法读取大小的记录：直接排除，分类保留未导出原因。没有“大小未知”类别，不将这些记录及其 JSON 元数据计入估算。
- 预估阶段会检查和准备内容；缺失、损坏、读取失败或无法取得长度的记录直接进入未导出清单，正式导出不再处理这些记录，最终报告保留预估失败原因。取消和磁盘不足终止预估。正式导出仅打开准备好的传输文件并验证长度和哈希，不重建 Profile、不再次准备或生成传输文件；文件已不存在时按文件缺失跳过，即使原文件仍完整也不重新生成。

`HistoryRecord.Size` 在不同类型下的含义可能不同，不能直接求和作为传输字节数。预估仅供判断规模，不承诺精确大小或严格上界。实际写入时展示已处理的附件字节数，不为预估制作附件副本。

预估结果和数量只用于内部计划与界面，不写入归档。不查询磁盘剩余空间；实际生成传输文件或写入输出遇到磁盘不足时报告失败，并清理本次未提交输出。

### 对话框宿主和焦点

设置页入口绑定主窗口，历史入口绑定历史窗口，目录选择器使用相同宿主。WinUI3 当前文件夹选择器固定使用主窗口，接入时需支持历史窗口宿主。

从历史窗口打开导出时，在模态窗口及目录选择器生命周期持有可释放的“模态操作保持显示”作用域。`OnLostFocus()` 在作用域内不因 `CloseWhenLostFocus` 隐藏窗口；结束后恢复原有行为，不修改用户置顶和失焦设置。不要复用会被 `OnGotFocus()` 重置的 `_remainWindowForViewDetail`。

模态打开期间，历史列表的复制、粘贴、删除和 Esc 退出多选等快捷键不抢占输入。验证置顶历史窗口不遮挡导出对话框或目录选择器，macOS 额外验证窗口隐藏、Space 和焦点切换。

## 文件格式

### 归档结构

无附件时输出一个 UTF-8、可读缩进的 JSON 文件。有附件时输出普通 ZIP：

```text
SyncClipboard-history-20261009-153000.zip
├── history.json
└── files/
    ├── Image-{hash}/
    │   └── image.png
    ├── Text-{hash}/
    │   └── full-text.txt
    └── Group-{hash}/
        └── group.zip
```

JSON 文件和 ZIP 中的 `history.json` 使用同一结构；文件中包含版本信息，不另设一份重复的 manifest。所有附件引用使用归档内相对路径和 `/` 分隔符，不输出原机器绝对路径作为恢复依据。每条记录的目录名使用 `Profile.GetProfileId(type, normalizedHash)`，即 `{Type}-{Hash}`，完整路径为 `files/{profileId}/{transferFileName}`。哈希按导出记录中的规则规范为大写，不截断；目录名不依赖导出顺序或数据库 ID，也不使用本地工作目录的 `{Type}_{Hash}` 命名。

示例中的 `{hash}` 代表实际完整哈希。传输文件名独立保存在元数据中，实际名称来自传输数据描述并进行安全规范化。生成的 Profile ID 必须是合法的单个路径段，异常身份应报告错误，不能通过替换字符将不同身份映射到同一目录。相同 Profile ID 的附件路径只能写入一次；发现相互冲突的重复内容时报告错误，不静默覆盖。

Group 的传输 ZIP 是外层导出 ZIP 中的一个普通文件，不展开为多个附件。用户解压外层归档后可以再解压 Group 传输包查看原文件；外层打包可以对已压缩附件使用不压缩模式，但不得改写附件字节。

### 文档和记录模型

新增独立的 `HistoryExportDocument` 与 `HistoryExportRecord`，不直接序列化 `HistoryRecord`、`ProfileDto` 或 `ProfilePersistentInfo`。历史记录快照直接转换为 `HistoryExportRecord`，此时将类型转为字符串、哈希转大写、时间转 UTC；预估和正式导出始终复用同一记录模型，不再保留 `HistoryExportItem` 或第二次模型转换。本机原文件路径、传输文件路径/哈希及计算属性标记 `JsonIgnore`，仅在准备与报告阶段使用，不写入备份。

| 文档字段 | 含义 |
| --- | --- |
| `format` | 固定值 `syncclipboard-history` |
| `formatVersion` | 本期为 `1`，独立于数据库和配置版本 |
| `appVersion` | 创建文件的客户端版本 |
| `exportedAt` | UTC ISO 8601 导出时间 |
| `records` | 通过完整性验证并实际导出的历史记录数组 |

导出范围用于程序内部选择记录，结果统计用于界面和独立报告，均不写入归档文件。

| 记录字段 | 含义 |
| --- | --- |
| `type`、`hash` | 内容类型字符串与原内容身份，哈希统一大小写 |
| `text` | 原记录的文本元数据，原样保留；短文本是全文，长文本是预览，其他类型按原描述保存 |
| `size` | Profile 内容大小：先保留历史记录原值，准备后采用 `Profile.GetSize()` 返回的缓存值或新计算值；不使用传输文件字节数替代 |
| `timestamp`、`lastModified`、`lastAccessed` | UTC ISO 8601 时间 |
| `starred`、`pinned`、`from` | 收藏、置顶和来源；导出字段使用正确拼写 `starred` |
| `hasTransferData` | 此记录是否需要传输文件；为 `true` 时必须附带完整文件 |
| `transferData` | 已验证传输文件的描述，含 `name`、归档相对 `path`、实际字节数 `size` 和 `sha256`；仅无需传输文件时为 `null` |

传输文件描述只保存本次已取得并验证的文件，描述在准备阶段确定，实际打包按该描述验证字节数和哈希，成功后原样写入清单。`hasTransferData == false` 且 `transferData == null` 表示无需附件，例如短文本；`hasTransferData == true` 时，`transferData` 和对应文件必须同时存在。不能取得完整文件的记录不进入 `records`。存在传输文件时，JSON 中的 `text` 不代表完整内容，长文本尤其不能用预览冒充全文。

文本元数据不修剪空白、不转换换行；传输文件逐字节复制，不重新编码或重复将长文本全文写入 JSON。`hash` 是 Profile 内容身份，`transferData.sha256` 是此次传输文件的字节哈希，两者不能混用。记录 `size` 的单位沿用 Profile 语义（例如文本为字符数、文件为字节数），与始终表示文件字节数的 `transferData.size` 区分，不能当作归档总字节数。未知类型通用回退保留原记录的 `size`，不尝试推导。

不导出数据库 ID、`SyncStatus`、远端 `Version`、删除墓碑及本地可用性内部标志。归档只包含完整记录，不设置完整性状态或错误字段。是否可导出由此次实际验证决定，不能直接信任 `IsLocalFileReady`。未来导入可基于版本化格式实现，但本期不实现导入接口或其去重、合并、同步策略。

记录按 `Timestamp` 降序，再按类型和规范化哈希稳定排序。使用流式 JSON 写入，避免将全部长文本和附件同时加载到内存。

## 统一传输文件导出流程

| 当前类型示例 | 导出的传输文件 | 格式影响 |
| --- | --- | --- |
| 短文本 | 无，文本元数据包含全文 | 无其他附件时为 JSON |
| 长文本 | 完整文本传输文件 | 成功收集时为 ZIP，即使没有其他附件 |
| 图片 | Profile 提供的图片传输文件 | 成功收集时为 ZIP |
| 单文件 | Profile 提供的文件本身 | 成功收集时为 ZIP |
| 文件组 | Profile 提供的完整传输 ZIP | 成功收集时为 ZIP，外层归档中保留该 ZIP |
| 未来新增类型 | Profile 提供的传输文件，不要求导出层理解内部格式 | 成功收集时为 ZIP |

上表仅说明现有类型的结果，不能实现为导出层按 `ProfileType` 分支。统一流程如下：

1. 准备阶段从快照重建独立 Profile，依据 `HasTransferData` 判断是否需要附件。无需附件时仅保留文本元数据，不为短文本人为创建文件。
2. 已有传输文件优先校验并直接读取原文件流，保留完整字节，不复制到临时目录，不解包或重打包。存在可信持久化 `TransferDataHash` 时核对字节；缺少该绑定时由 Profile 校验内容身份，不能只新算一个哈希就宣称文件属于该记录。
3. 仅在准备阶段，没有可用传输文件但本地内容完整时，调用现有 `PrepareTransferData` 能力，在 Profile 的正常传输数据位置生成文件，然后直接读取。生成的是传输文件本身，不是已有附件的导出副本，不额外建立导出专用临时目录或预备副本集合。
4. 每条记录在写入前验证源文件可读且身份有效；读取过程中同时计算实际字节数和 SHA-256。只保存源引用、期望哈希及元数据，不保存附件快照。
5. 开始写入该附件前，准备好的文件已不存在时按文件缺失跳过整条记录并保存原因，不回退原文件或重新生成传输包。不会仅导出该记录的元数据，也不会用残缺原文件生成看似完整的 Group 包。附件写入中途的失败按下文归档失败规则处理。

重建传输文件可能得到与旧传输包不同的字节哈希，例如 ZIP 容器元数据变化；必须验证其 Profile 内容身份与原记录一致，并记录新文件的字节哈希。复用现有有效传输文件时则保证字节完全相同。

导出层不调用本地化收集 Group 子项，不自行遍历其内部目录或新增类型哈希算法；类型知识留在 Profile 层。必要的新传输文件沿用原有生成位置，不写回历史记录时间、同步状态或触发上传。传输文件属于应用运行中使用的数据，导出流程不管理其生命周期，不在成功、失败、取消、关闭或重新预估时删除；`PrepareTransferData` 保持原有两个参数，不提供新建文件登记回调。生成文件时的内部原子写入沿用 Profile 机制，不要求移除其自身保障；导出不得覆盖用户原文件或主动删除复用的传输文件。

新增类型只需接入已有 Profile 工厂和传输契约，就能复用导出流程。对于当前程序完全无法重建的类型，如存在持久化传输哈希的文件绑定，预估时也必须读取并校验实际文件后才能纳入导出，仍可按通用文件契约导出完整记录；否则跳过并报告缺少处理能力或验证依据，不猜测内容、不静默忽略。此兜底不等于承诺理解未来版本的数据库格式。

仅远端有内容但本地尚未下载的记录，因本地文件缺失而跳过，不触发网络请求。图片、文件、Group 或长文本内容缺失不会阻止其他完整记录导出；操作结束后统一报告成功数量与缺失跳过数量，不把跳过的记录写入归档。

## 快照和一致性

本期提供数据库元数据快照，传输文件直接从源读取，不创建内容副本，也不承诺数据库与外部文件的全局时间点快照。

1. 在 `HistoryManager` 的数据库同步边界内读取符合范围的非删除记录，复制数组等可变字段，形成脱离 EF 跟踪的快照后释放锁。大范围查询不得仅取 UI 已加载页；分批实现时须使用一致的数据库读事务，按稳定键遍历，不以会变动的分页偏移拼接不同时间点的数据。
2. 验证与读取尽量使用同一打开句柄，并采用平台允许的共享限制；不能假设所有平台都能阻止外部写入。传输文件直接流式写入目标，同时核对实际字节数和哈希。
3. 源文件被同步、清理或外部程序删除、替换时，通过打开、读取或校验失败报告受影响项；没有暂存副本提供隔离。内存只保留元数据、结果及有界读写缓冲。
4. 不为导出长期持有 `_dbSemaphore`，不暂停上传、下载或清理；没有附件的记录也不修改访问时间来避免清理。

导出范围使用预估时的同一份快照，不在开始后重新查询改变范围。快照后新增记录不纳入；删除记录若内容仍可验证则可导出，否则按实际原因跳过或失败。

### 条目失败与归档失败

创建某个 ZIP 条目前，打开并验证准备阶段确定的传输文件；可识别的缺失、损坏等源数据问题在此时跳过。只有附件完整写入且哈希一致后，记录才进入成功候选集合。

一旦条目已开始写入，若发生中途读取失败、源内容变化或目标写入失败，整次归档失败并删除未提交输出。首版使用 `ZipArchiveMode.Create` 流式写入，不能假设可删除已写入的残缺条目；也不使用会缓存附件的 Update 模式，不为单条回滚引入自制 ZIP 写入器。

这一边界让常见的缺失记录可以跳过，同时避免在没有附件副本的情况下发布残缺归档。整次失败时，前面已写入但未提交的候选记录也不计成功，报告分别说明具体源错误与因归档未提交而未保存的记录。

## 写入和失败处理

遇到第一个已验证且可读取的传输文件时才创建外层 ZIP，后续附件逐条流式写入。全部处理结束后，将成功候选集合写为 ZIP 内的 `history.json`，再关闭并提交 ZIP。若没有成功附件但有完整内联记录，直接生成 JSON；没有完整记录时只在已选目录保存报告。Group 内部文件和目录不单独计数。

最终文件提交成功后，显示“已导出 28 条记录，2 条记录因文件缺失未导出”。统计按记录计数，一条 Group 缺少多个原文件仍只计为一条未导出记录。准备阶段若没有有效传输包且无法从本地取得完整内容，计为缺失；准备时重建成功不计入跳过。正式打包时若准备好的传输文件已丢失，直接计为缺失，不再重建。

损坏、校验不通过、无权限、缺少类型处理能力以及快照查询时已失效的选择分别记录为其他未导出原因，不混入“缺失文件”数量。有这些情况时在结果中补充“K 条记录因其他原因未导出”并提供明细。每条请求记录只计入一个最终分类。统计用于内部结果、界面和独立报告，不写入 JSON／ZIP 归档。

“已导出”数量必须与成功提交文件中的 `records` 数量一致。取消或目标写入失败时不把已准备条目计为成功，显示取消或失败；全部因缺失而跳过时显示导出 0 条及缺失数量，不宣称已生成文件。

源文件流直接写入所选目录中唯一的 `.partial` 输出文件，关闭并校验完成后在同一目录改名为最终 `.zip` 或 `.json`。这只是最终归档的写入中名称，不是附件暂存目录，完成后也不再复制一次归档。文件名冲突追加编号，创建与提交均不覆盖旧文件。目录不可写或消失时报告失败，不在中途重新弹出位置选择器。

| 场景 | 行为 |
| --- | --- |
| 用户取消导出 | 释放句柄，删除未提交输出，在已选目录保存已知结果报告 |
| 无记录 | 已选目录中不生成归档或报告 |
| 全部选择失效或全部记录不完整 | 不生成归档，仅在已选目录保存报告并显示数量及路径 |
| 条目开始写入前发现源文件缺失 | 跳过整条记录，结束后计入“因缺失文件未导出” |
| 条目开始写入前源文件无权限、损坏或校验失败 | 跳过并单独报告原因，不计作缺失 |
| 条目写入中途读取或校验失败 | 整次归档失败，删除未提交输出，不能保留残缺条目 |
| 数据库读取失败、生成传输文件时磁盘不足、归档写入失败 | 整次任务失败，不发布半成品，不覆盖已有文件 |
| 无法重建 Profile 的记录类型 | 有可验证传输文件时通用复制；否则跳过整条记录并报告缺少处理能力或验证依据 |
| 用户取消或关闭导出窗口 | 请求取消并等待收尾；清理失败提示残留路径。应用被强制终止时可能残留 `.partial`，不视作成功归档 |

只清理由本次任务创建的未提交输出，不删除源文件、复用的传输文件、已提交归档或报告。内部结果使用稳定问题代码供界面和报告分类，不向归档写入错误明细；日志不主动写入完整剪贴板文本或凭据内容。

外层 ZIP 条目名必须由受控的相对路径生成，禁止绝对路径、`..`、重复目标和越界。内层传输文件作为完整字节流保存，导出层不展开它；Profile 自身校验或生成传输文件所需的临时操作沿用现有安全约束。磁盘不足视为整次任务失败。实现使用现有 .NET JSON、ZIP 能力，首版无需增加 Excel 或第三方归档依赖。

## 未导出记录报告

使用 UTF-8 纯文本 `.txt` 文档，方便直接打开和搜索。操作结束且存在未导出记录时自动生成，无需用户再次选择保存路径；全部成功时不生成空报告。报告独立于归档，不放进 `history.json` 或 ZIP，也不恢复归档中已删除的统计和错误字段。

报告始终保存在开始时选择的目录，名称为 `{本次导出文件名主体}-not-exported.txt`。同名追加编号，不覆盖旧报告。全部记录被跳过时，仍使用已选目录和本次文件名主体，不再询问位置，也不新增应用内报告目录。

报告包含：

- 操作时间、最终状态，以及实际生成的归档路径；没有归档时明确写“未生成归档”。
- 请求记录数、成功导出数、因缺失文件未导出数及其他原因未导出数，与界面保持一致。
- 每条未导出记录的 Profile ID、类型、记录时间、来源及文本预览或文件名，足以让用户在历史中识别该记录。已失效的选择至少保留请求中的类型和哈希，其余字段标记为不可用。
- 具体未导出原因，例如“本地传输文件及原文件均不存在”“文件读取被拒绝”“传输文件校验不通过”。存在相关路径时列出原传输文件路径及已知缺失源路径，便于定位；不为报告重新遍历 Group 或重复读取附件。

每条记录使用独立文本段落，预览最多保留 200 个 Unicode 字符并标明截断，不把完整长文本或二进制数据写入报告。问题说明使用可读文案，可附内部问题代码，不直接输出异常堆栈。报告中的路径是用于排查的本机路径，与归档内部的相对路径用途不同。

成功数量以最终提交为准。整体写入失败时，已写入但未提交的记录标为“归档写入失败，未保存”，不计作成功。若源文件在复制过程中读取失败或内容变化，出错的那条记录保留具体源失败原因，其余未提交记录才标为归档失败；目标写入失败不归因于源文件。取消时保留已确认原因，未检查条目标为“操作取消，未检查”。取消位置选择或仅预估后关闭不生成报告。若数据库错误导致范围无法完整取得，只报告已知信息并说明数量未知，不编造明细。

结果窗口等待报告写入结束后显示数量和实际完整路径。所选目录无法保存报告时，提示“未导出报告保存失败”及原因，保留界面明细供复制或重试，不静默改存其他目录，不虚报路径。报告失败不删除成功归档，二者结果分别展示。

## 代码结构

| 新增或调整项 | 职责 |

| Core `ViewModels/HistoryExportViewModel.cs` | 位置选择、预估、开始、取消、数量、归档与报告路径展示 |

| `Strings.resx` 与 `Strings.zh-CN.resx` | 导出文案和结果信息 |

对话框呈现器可沿用普通注册对应主窗口、键控 `HistoryWindow` 注册对应历史窗口的方式。模态组件每次独立创建，导出工具负责任务互斥。`HistoryExporter` 为按需调用的工具，不实现常驻 `IService`；保持单例注册以共享导出互斥状态。目录选择器通过平台回调或小接口提供，不让 Core 持有窗口、`XamlRoot` 或选择器对象。

位置选择后在后台调用 `GetExportSnapshotAsync(selected)` 和 `EstimateAsync(snapshot, selected, token)`，返回含准备成功的快照记录、估算大小和未导出清单的 `HistoryExportPlan`。用户开始后调用 `ExportAsync(plan, destinationDirectory)`，在一次流程中逐条验证、读取和写入。计划不持有附件副本，不再拆成“全部附件复制完成”和“开始输出”两个阶段。`finally` 释放源流、归档和目标句柄，并清理未提交输出。导出计划只保存数据，不需要释放；新生成和已有传输文件均保留。

操作结束时统一调用报告写入器，向界面返回归档路径、成功与未导出数量、报告路径或报告错误。报告使用独立于已取消导出令牌的收尾生命周期；记录信息保存在内部结果中，不依赖附件副本。

## 验收和验证

### 核心行为

- 位置确定后才预估，预估数量与后续使用的快照一致；仅对准备成功的记录按文件字节长度、JSON UTF-8 大小估算，失败记录计入导出前显示的选择总量，但不计入估算大小或实际导出成功数量。
- 预估可生成缺失的传输文件并按实际长度计入，正式导出沿用完整 `transferData` 并验证文件，不重新生成；准备后的文件丢失时跳过并报告文件缺失；不复制附件或下载内容。无法准备的记录直接跳过并保留报告原因；取消和空间不足终止预估。
- 只有短文本时导出为 JSON，全文、空白、换行、Unicode、时间、来源、收藏、置顶一致。
- 仅长文本或短文本与长文本混合时，只要保留的完整记录包含传输文件就导出 ZIP；附件完整保留原字节，JSON 保存预览和有效的 `transferData` 引用。长文本文件缺失时整条记录跳过，不得用预览冒充全文。
- 图片、文件、文件组与文本混合导出为 ZIP，JSON 引用的每个传输文件存在且校验匹配；Group 传输 ZIP 保持完整字节，原目录层级包含在传输包内。
- 缺少现成传输文件但本地内容完整时，通过统一能力生成并验证文件；重建传输包与记录的 Profile 内容身份一致。原文件残缺且没有有效传输包时跳过整条记录，不输出残缺 Group 包。
- 使用仅提供统一传输能力的测试 Profile，验证新增类型无需修改导出工具即可输出元数据和传输文件；已有文件缺少可信哈希绑定时验证内容身份，不接受错误文件。
- 写入条目前发现缺失时跳过，元数据和附件均不进入归档；仅剩短文本时输出 JSON，有传输文件时输出 ZIP，全部跳过时仅在已选目录生成报告。
- 已有传输文件直接流式读入目标，不制作附件副本，内存占用不随附件总量增长；文件在条目写入中途变化、读取失败或校验失败时不发布残缺 ZIP，清理未提交输出并如实报告整次失败。
- 成功数量等于已提交文件的记录数量，缺失按记录计数，不按文件数计数；校验失败、无权限、失效选择等其他原因不误计为文件缺失。
- 报告逐条列出未导出记录及实际原因，数量与最终结果一致；整体写入失败和用户取消不会被误写成文件缺失，已准备未提交的记录不计成功。
- 报告与归档始终在已选目录保存，全部跳过时仍在该目录保存报告；重名不覆盖，写入失败不虚报路径或删除成功归档。
- 全部导出覆盖所有分页且排除删除记录；选中导出覆盖跨分页、跨筛选的选择，不包含未选记录。
- 同一 Profile 的导出目录不随记录顺序变化，使用完整、规范化的 `Profile.GetProfileId`，且 JSON 附件引用与实际路径一致。不同 Profile 的同名传输文件相互隔离，重复身份冲突和不安全路径不会造成覆盖或越界。
- 导出不改变数据库内容、访问时间、同步状态、剪贴板及用户原文件，不触发网络下载或上传；必要的新传输文件沿用原有生成位置，生成后保留，导出计划不负责清理。
- 源文件读取中变动、缺失、无权限以及校验失败有明确结果；目标写入失败和取消不破坏已有目标，不留下被视为成功的半成品。
- 大附件流式处理，进度可更新、取消可响应，不把整个 ZIP 加载进内存。

### 界面行为

- 两个入口使用同一模态组件，先选择目录，无选中项时按钮禁用；位置选择取消不读取附件或生成文件。
- 用户点击“开始导出”前能看到条目数量和估算大小；未导出信息仅在结束后展示，预估中可以取消，不出现磁盘剩余空间检查或容量确认步骤。
- 文件扩展名与最终内容一致，导出中途不再弹出位置或格式选择器。
- 写入前识别的不完整记录自动跳过，结束后显示数量与报告路径；全部跳过时显示 0 条及已选目录中的报告，整次失败不把已写入未提交记录计为成功。
- 历史窗口不因模态或目录选择器失焦而隐藏，置顶不遮挡选择器；关闭后恢复原有行为并保留选择状态。
- 连续重复点击或从另一个入口发起不会启动并行导出；取消、失败后可重新开始。
