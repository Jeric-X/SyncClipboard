## 1. 协作方式与合入条件

### 每个 PR 的固定流程

1. **开始前：** 我从前一步已合入的 master 建立独立 `codex/upgrade-XX-主题` 分支，列出本步文件、版本、行为变化和你的检查项。尚未合入时不启动下一个升级 PR，也不预先堆叠一串依赖分支。
2. **实现与自动检查：** 只移植当前主题及其必要修复、测试和 CI。先通过本地适用检查，且须等用户明确要求提交后再提交新 PR；提交后监控当前 head 的 CI、代码评审、行内线程和普通评论，失败在当前 PR 修复。
3. **交给你检查：** CI 与可处理评审问题清理后，我提供明确的提交 SHA、变更说明、适用平台、逐项 UI 清单、预期结果，以及针对该版本的构建/启动说明。你检查下面“你需要检查”的内容，反馈通过或具体问题。
4. **修复后复验：** 代码变更产生新 SHA 后，重新等待 CI；你只复验受影响的手工项和必要的基础冒烟，不要求无理由重复整套检查。旧 SHA 的 UI 结论能否沿用须明确说明。
5. **合入：** 自动检查通过、评审无可处理问题、必需手工项通过或由你明确接受未覆盖项后，由你合入；需要我代为合入时，另行明确授权这个 PR。合入前若更新了基线，按新 head 重验。
6. **进入下一步：** 确认合入后 master 的适用 CI 成功，记录合入提交及验收结果，停止本 PR 的监控，再准备下一步。

“CI 干净”“待你验收”“可合入”“已合入”是四个不同状态。只剩你验收或决定时，停止轮询并等待你的反馈，不自动继续升级。

### 验证分工

| 内容 | 我负责 | 你负责 |
| --- | --- | --- |
| 代码、版本与兼容性 | 最小迁移、源码/依赖解析、自动测试、CI 与评审修复 | 审核变更是否符合预期，决定支持范围和行为取舍 |
| 界面和系统交互 | 给出操作清单与预期，分析你报告的问题；默认不代操作桌面 | 启动、窗口、设置、剪贴板、拖拽、热键、托盘、通知、退出/重启等真实验收 |
| 平台设备 | 用对应 CI 覆盖编译和非 UI 测试，标注手工覆盖缺口 | 记录实际测试的 OS、架构、显示缩放、桌面环境；指定可参与的其他测试者 |
| 产物 | 完全信任 CI 编译和打包结果，不下载或复用远程产物做二进制、包结构、签名或哈希审计 | 可自行选择本地构建或该 PR 的 CI 包来做运行/安装体验验收，无需审计二进制 |

必要的额外二进制检查仍只限于本地编译的 macOS 版本，且必须有具体问题，不能变成每步例行任务。协议数据完整性、图片内容和数据库校验不属于产品二进制审计，继续保留。

这次的 UI 项是**待你验收**，不是自动排除，也不把编译或 mock 成功当成 UI 通过。macOS 锁屏时我可以继续非 UI 工作，你的桌面操作等到可操作会话再进行；没有 Windows/Linux 设备时如实记为未覆盖，由你决定补测、暂缓，或接受具体风险。尤其托盘、全局热键和退出/重启不能只凭 CI 宣布通过。

**H0：桌面基础冒烟。** 适用于下文标明的平台，每次使用该 PR 指定 SHA 的版本：

1. 启动应用，打开主窗口和历史窗口；无崩溃、空白窗口或明显缺失文字。
2. 关闭主窗口后从托盘重新打开；行为与基线一致，不出现重复窗口。
3. 打开一个已有设置页，查看值；修改一项可恢复设置，重启后仍保存，随后恢复。
4. 在测试编辑器复制一段文字，从历史中复制/粘贴回来；内容完整，目标应用和焦点符合基线行为。
5. 正常退出，再启动；没有残留托盘、重复实例或无法再次启动。

H0 不替代各步专项清单。Windows 原生 WinUI3 与 Windows Avalonia 备用入口分别记录，不互相代替；没有使用备用入口时写明未测。

## 6. 如何避免再次变成大 PR

**只移植主题相关的最终修复。** 上述提交号是定位线索，不是可直接执行的 cherry-pick 列表。重点审查中央包表、项目文件、AppCore、退出入口、HistoryManager、测试和工作流这些被多步反复改过的文件。每步用当前 master 重建最小 diff，不能复制最终 net10/Quartz4 的文件到仍需旧版接口的阶段。

**源码/测试/文档归属于引入行为的 PR。** 对应功能测试随功能 PR 加入，最小可复现输入纳入仓库；临时 `/tmp` 脚本、个人旧库和历史日志不是新 PR 的可复现依赖。不要一次搬入 #419 的整个验证体系，也不要为纯版本核定再跑全套 UI 或造空提交。UI 行为需要的证据由本方案手工清单补齐。

**控制审阅范围。** 除机械迁移外，通常争取一个 PR 可在一次审阅中理解；若混入多个不相关失败原因就拆分。Avalonia、Quartz 是已知可能较大的兼容单元，提交前明确列出机械改动、真正行为改动及对应验收，不能只说“升级依赖”掩盖几十个页面或生命周期变化。PR 描述只写修改内容、产生的变化和独立列出的不兼容风险，不写总体步骤编号、验证结果或验收清单；验证与验收单独在对话中提供。

**适量验证。** 本地按影响范围构建/测试；共享 obj 的构建串行运行，不为等待超时就重复启动相同命令。PR 原有必需 CI 不删；新增探针只放到相关平台任务，合理复用已有服务启动和测试报告。得到有效结果后不再重复审计产物或为同一证据反复触发新提交。

**风险在对应步骤解决。** S3 的独立问题在安排 PR-14/15 前确认范围；MVVM 属性迁移与初始化改造已取消；退出/取消的兼容问题在 PR-20 内处理。遇到其他已有缺陷，先记录并独立修复或由你决定处理；不能用后面的升级遮住当前失败。

**回退。** 单步已合入后发生问题，用新的 revert 或修复 PR 保留历史，不强推 master。数据库/配置可能已被使用过，回退代码不等于恢复数据；使用检查点00保存的测试副本，实际用户数据另行设计恢复。若后续 PR 已依赖本步，应先评估逆序回退或修复，不能撤掉前置依赖却保留后续 TFM/API。
